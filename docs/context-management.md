# Context Management Guide

This document explains the current context management system in `ainovel-cli`, including:

- Why context management exists
- Where context comes from
- How runtime compression, recovery, and handoff work
- The value, trigger conditions, and use cases of each strategy
- Where to look first when something goes wrong

The goal is not to introduce abstract concepts, but to let future maintainers quickly understand the current implementation and troubleshooting entry points from this document alone.

## 1. Design Goals

The context management in this project is not for generic chat. It is designed for novel writing and must solve several problems at once:

1. Long conversations can exceed the model's context window.
2. What novel creation needs to retain is not the "chat history itself," but structured narrative memory.
3. The Writer must not lose character states, foreshadowing, chapter plans, style constraints, or pending review/rewrite items after compression.
4. When resuming writing, we cannot assume the model still "remembers what was discussed before"; we must prioritize relying on persisted artifacts.

So we use a layered memory scheme:

- Short-term Memory: The tail of recently retained messages.
- Mid-term Memory: The `ContextSummary` generated by compression.
- Long-term Memory: Structured artifacts in the project store.
- Restored Memory: Handoff / restore pack / `novel_context`.

## 2. General Architecture

### 2.1 Major Layers

The current context management is divided into four layers:

1. `agentcore/context`
   Responsible for general context budgeting, strategy pipeline, and compression/recovery framework.

2. `internal/tools/novel_context`
   Responsible for assembling structured data from the novel project into the available context for the current turn.

3. `internal/agents/ctxpack`
   Provides Writer-specific fast compaction based on store data.

4. `internal/agents/ctxpack/restore.go`
   Appends a post-compaction restore pack after `FullSummary` so Writer can continue.

### 2.2 Data Flow

There are two main context paths at runtime:

1. Normal Work Path
   - Agent calls `novel_context`.
   - `novel_context` reads chapter summaries, plans, characters, timelines, etc., from the store.
   - These data enter the current turn's prompt.

2. Out-of-Context Path
   - `ContextManager` detects token pressure.
   - Compresses according to the strategy sequence.
   - First tries lightweight compression and store-based compression.
   - If still not enough, it resorts to LLM `FullSummary`.
   - Injects the restore pack after `FullSummary`.

## 4. How ContextManager is Assembled

All three Workers use `newContextManager`, rebuilt by their `ContextManagerFactory` against the current model window for each run (including after `/model` switches). Writer configuration lives directly in `build.go`; Architect/Editor share `roleContextProfile` with different summary prompts and retained-read counts.

Key parameters of the current `contextManagerConfig`:

- `ContextWindow`
  The model's total context window.

- `ReserveTokens`
  Reserved headroom before compaction, computed by `bootstrap.CompactReserveTokens`: 15% of the window, with a minimum of 8,000 tokens.

- `CommitProjected`
  Whether to commit compaction as the new baseline. All three roles use true, avoiding repeated prefix rewrites that invalidate prompt caching.

- `ToolMicrocompact`
  Configuration for tool result micro-compression.

- `ExtraStrategies`
  Additional project strategies. Currently only Writer uses `StoreSummaryCompact`.

- `Summary`
  `FullSummary` configuration, including role-specific prompts and post-summary hooks.

Current configuration:

| Parameter | Writer | Architect | Editor |
|------|--------|-----------|--------|
| Microcompaction scope | All tool results | `novel_context` only | `novel_context` only |
| Recent results retained | 5 | 3 | 2 |
| Microcompaction minimum | 200 tokens | 200 tokens | 200 tokens |
| ExtraStrategies | StoreSummaryCompact (retain 20,000 tail tokens) | None | None |
| Summary prompt | Novel narrative (ctxpack) | Planning checkpoint | Review checkpoint |
| PostSummaryHook | writerRestorePack | None | None |

Compaction triggers at `ContextWindow - ReserveTokens`: 170K for a 200K window, or approximately 109K for 128K.

Cut points align to complete tool groups (`agentcore/context.FindCutPoint`). If the token boundary lands on a tool result, move back to its initiating assistant call and retain the whole group in the tail. Workers have one task message followed by tool groups; searching forward for a user boundary would reach the end and abandon compaction every time.

Current strategy order:

Writer：

1. `ToolResultMicrocompact`
2. `StoreSummaryCompact`
3. `FullSummary`

Architect / Editor：

1. `ToolResultMicrocompact`
2. `FullSummary`

This sequence has a signature:

- Remove tool noise using the cheapest method first
- If store data is sufficient, Writer compacts structured data without an LLM call
- Fall back to an LLM summary last

Architect/Editor microcompact only old `novel_context` results, since they can reread that store data. Write-tool results (`save_*`) and chapter prose from `read_chapter` are task facts and evidence: they remain intact until final `FullSummary` summarization.

`novel_context` does not truncate sections against a fixed byte budget. It selects task-relevant data (focused arc, recent window, active foreshadowing); each Worker manages size against the real model window. A hard tool-size error offers no useful user action, whereas the model window is configurable.

## 5. What Each Strategy Does

### 5.1 ToolResultMicrocompact

Implementation Location:

- `../agentcore/context/strategy_tool.go`

Functions:

- Clean up historical `tool_result` messages.
- Replace old tool results with short placeholder text.

Value:

- Tool return contents are usually large in volume and low in information density.
- Many old tool results are just "process noise," not novel memory.

Current configuration characteristics:

- Writer covers all tool results and retains the latest five
- Architect/Editor cover only `novel_context`, retaining three and two respectively; only the latest read with identical arguments is protected
- Results below 200 tokens are retained because they may be the only record of a state transition

Applicable Scenarios:

- After multiple Writer read/check/draft calls
- During repeated volume/arc-focused long-form Architect reads
- During chapter-by-chapter Editor context reads over a review range

### 5.2 LightTrim

Implementation Location:

- `../agentcore/context/strategy_trim.go`

Functions:

- Truncate very long text blocks.
- Keep the head and tail, replacing the middle with placeholders.

Value:

- Keeps the message structure intact.
- Low cost.
- Very suitable for handling ultra-long chapter texts or massive outputs.

Applicable Scenarios:

- A single message is too long, but the entire history does not need to be summarized yet.

Current status: provided by agentcore but not used by any project Worker pipeline. It skips recent messages and hard-truncates text blocks at both ends, potentially breaking JSON from `novel_context`. Removing an old tool result entirely and rereading is more appropriate.

### 5.3 StoreSummaryCompact

Implementation Location:

- `internal/agents/ctxpack/strategy.go`
- `internal/agents/ctxpack/builder.go`

Functions:

- When the Writer's context is too long,
- Prioritize using structured memories in the persisted store to replace old messages.
- Does not call the LLM.

It is not a dialogue summary, but "structured memory replacement."

"Current Task" is a fixed section in every Writer summary: store summaries and LLM summaries (`WriterSummaryPrompt`) both preserve it. The first compaction reads the initial user message; later compactions extract it from the previous summary up to the next heading. Alternating summary formats therefore preserves the task. Store data contains novel facts, not the current assignment; otherwise Writer could remember the novel but forget what it must do. Legacy Chinese task headings remain readable for older checkpoints.

Core data currently retained:

- Current progress.
- Recent chapter summaries.
- Current chapter plan.
- Current chapter outline.
- Current arc summary.
- Current volume summary.
- Character snapshot.
- Active foreshadowing.
- Pending review/rewrite issues.
- Recent timeline.
- Style rules.

Trigger Pre-requisite:

- The current chapter is greater than 1.
- There are already enough historical summaries in the store.
- And the current chapter has at least work-state data:
  - `chapter_plan` or `current_outline`.

Value:

- Reduces the number of LLM compressions.
- Avoids drift of key novel information during summary.
- Makes long-term memory prioritize landed facts rather than chat history.

Why only used for the Writer:

- This is a novel-domain strategy, not a general framework strategy
- It targets chapter-writing state (plan, outline, unresolved issues). Architect/Editor have single tasks with repeated reads and can discard old `novel_context` results and reread instead of replacing history with store data
- Writer is the appropriate first validation target because it most needs continuous creative memory

### 5.4 FullSummary

Implementation Location:

- `../agentcore/context/strategy_summary.go`
- `../agentcore/context/summary_run.go`

Functions:

- When the layers above are still not enough, use the model to generate a `ContextSummary`.
- Retain the tail of recent messages.
- Turn earlier context into a structured checkpoint.

Where the Writer differs from the default code assistant:

- Writer uses a custom summary prompt
- The summary explicitly preserves:
  - Current task verbatim
  - Current progress
  - Current character state
  - Active foreshadowing and clues
  - Review feedback and unresolved issues
  - Style and pacing
  - Key decisions
  - Next steps
  - Essential context

Architect/Editor each use checkpoint-style prompts (`architect_context.go` / `editor_context.go`):

- Architect preserves current task, hard constraints, confirmed facts, planning decisions, pending items, and next steps, distinguishing saved results from unsaved proposals
- Editor preserves current task, authorization and acceptance constraints, evidence read by chapter number, findings, tool progress, and next steps; it may not claim to have read unread chapters

Neither uses a restore pack. After compaction they can reread facts and prose via `novel_context` / `read_chapter`. For long Editor tasks such as volume summaries, earlier chapter quotations pass through summarization and may be less precise than direct quotations.

Value:

- It is the final fallback strategy.
- Even if store data is insufficient, continuity can still be maintained through the LLM.

### 5.5 Circuit Breaker

Implementation Location:

- `../agentcore/context/engine.go`

Functions:

- When compression fails consecutively up to the threshold (default 3 times), skip the current round of compression.
- When skipping, a `RewriteEvent` (`Reason = "circuit_breaker"`) is still emitted.
- The TUI will display the scope as "skipped."
- Employs a half-open mode: retries next time after skipping a round, resetting on success and skipping again on subsequent failures.

Why it is needed:

- LLM summaries can fail consecutively due to network, model refusal, etc.
- Without a circuit breaker, every Project round would try and fail, wasting API calls.
- This waste accumulates in long novel writing sessions.

Troubleshooting:

- If the TUI continuously displays "skipped," it indicates a problem with the LLM summary path.
- Check context rewrite events in `slog` where `reason=circuit_breaker`.
- The circuit breaker does not affect `StoreSummaryCompact` (it does not call the LLM).

### 5.6 Token Estimation (CJK Aware)

Implementation Location:

- `../agentcore/context/usage.go`

Functions:

- All budget controls and compression trigger timings depend on token estimation.
- `estimateTextTokens` automatically detects if the text is dominated by CJK characters.
- CJK-dominated text: `runes * 1.5`
- ASCII-dominated text: `bytes / 4`

Why standard `bytes/4` cannot be used:

- One Chinese character in UTF-8 = 3 bytes.
- `bytes/4` would estimate one Chinese character as 0.75 tokens, while it is actually about 1.5 tokens.
- Underestimating by 2 times causes the compression trigger to lag seriously.

Impact Scope:

- `EstimateTokens` (one message)
- `EstimateTotal` (message list)
- `EstimateContextTokens` (hybrid: reported LLM usage plus estimated tail messages)
- Budget trimming in `ctxpack/builder.go`

Note: ToolCall args are JSON (ASCII-dominated), using `bytes/4`, unaffected by CJK adjustments.

## 6. Why the Writer Has Two Sets of "Post-Compression Memories"

The current Writer has two paths that look similar but carry different responsibilities:

### 6.1 StoreSummaryCompact

Responsibility:

- Replaces old messages directly during the compression process.

Features:

- Occurs before `FullSummary`.
- Zero LLM calls.
- Replaces earlier history with store data.

### 6.2 writerRestorePack

Implementation Location:

- `internal/agents/ctxpack/restore.go`

Responsibility:

- Appends a restore message after `FullSummary`.

Features:

- Occurs after LLM compression.
- Injected via `PostSummaryHook`.
- Used to supplement structured information that the Writer must see when resuming creation.

Why both are needed:

- `StoreSummaryCompact` is not guaranteed to hit (e.g., in chapter 1 or when store data is insufficient).
- Even if `FullSummary` is done perfectly, it might omit precise information in the store.
- So the restore pack acts as the final insurance.

Both now share `ctxpack/builder.go`, preventing divergent data selection.

## 7. Function of novel_context

Implementation Location:

- `internal/tools/novel_context.go`
- `internal/tools/novel_context_builders.go`

`novel_context` is not a compression strategy; it is the runtime "structured context assembler."

It categorizes store data into several types:

- `working_memory`
  - Current chapter plan.
  - Current chapter outline.
  - Recent chapter summaries.
  - Timeline.
  - Checkpoints.
  - Previous tail.

- `episodic_memory`
  - Character state.
  - Relationship state.
  - Recent state changes.
  - Foreshadowing.

- `reference_pack`
  - More stable settings and reference data.

- `selected_memory`
  - A small amount of key memories selected according to the current task.

Value:

- It determines the structured novel context truly "fed to the model" in each round.
- `StoreSummaryCompact` does not call it directly, but reuses the same data sources and assembly logic.

## 8. ContextProfile and MemoryPolicy

Implementation Location:

- `internal/domain/runtime.go`

### 8.1 ContextProfile

Function:

- Decides the loading window size based on the total number of chapters.

Current Rules:

- `<= 15` chapters
  - Recent `10` chapter summaries.
  - Recent `10` chapter timelines.

- `<= 50` chapters
  - Recent `5` chapter summaries.
  - Recent `8` chapter timelines.

- `> 50` chapters
  - Recent `3` chapter summaries.
  - Recent `5` chapter timelines.
  - Enable layered summaries.

Value:

- Controls context scale.
- Avoids stuffing all history into the prompt in long novels.

### 8.2 MemoryPolicy

Function:

- Explicitly writes down the current context usage policy.
- For `novel_context` output.
- For handoff / reminder / diagnostic logic.

Key Fields:

- `SummaryWindow`
- `TimelineWindow`
- `LayeredSummaries`
- `SummaryStrategy`
- `HandoffPreferred`
- `ReadOnlyThreshold`

Value:

- Turns "how the system should use memory" from implicit logic into an explicit runtime strategy.

## 9. Function of handoff

Implementation Location:

- `internal/orchestrator/handoff_policy.go`

When a work enters a longer, more complex phase that relies heavily on structured artifacts, the system leans towards handoff.

The handoff pack records:

- Current phase and flow.
- Next chapter position.
- Recent commits.
- Recent reviews.
- Recent summaries.
- Current memory policy.
- Recovery instructions.

Value:

- Interruption recovery does not depend on chat history.
- Prioritizes relying on structured artifacts in rework, review, and long-form scenarios.

## 10. Observability and Troubleshooting

### 10.1 Context Rewrite Events

Implementation Location:

- `internal/agents/context_manager.go`

Each context rewrite records a slog event through `contextRewriteCallback`, with `agent=writer|architect|editor` and these additional fields:

- `reason`
- `strategy`
- `committed`
- `tokens_before`
- `tokens_after`
- `messages_before`
- `messages_after`
- `compacted_count`
- `kept_count`
- `split_turn`
- `incremental`
- `summary_runes`
- `duration_ms`

This simultaneously enters:

- `slog`
- Runtime boundary queue.
- TUI `COMPACT` event.

### 10.2 What Can Be Seen in TUI

TUI displays:

- Current context tokens (with health color gradient).
- Context window.
- Current context scope (including "skipped").
- Current last strategy name.
- Number of summaries.

Color meaning of the context percentage (implemented in `internal/entry/tui/layout.go`):

| Color | Condition | Meaning |
|------|------|------|
| Green | < 70% | Ample, far from compression threshold |
| Yellow | 70-85% | Approaching compression threshold |
| Red | > 85% | Impending or ongoing compression |

TUI Scope Labels:

| Scope | Display | Meaning |
|-------|------|------|
| baseline | Base | Normal state |
| projected | Preview | Temporary compression preview |
| compacted | Committed | Compression applied |
| recovered | Recovered | Recovered after overflow |
| skipped | Skipped | Compression skipped by circuit breaker |

Value:

- Allows quick assessment of context health.
- Compression can be expected when yellow/red.
- Seeing "skipped" indicates a problem with the LLM summary path.

### 10.3 Where to Look First When Something Goes Wrong

#### Scenario 1: Writer loses chapter plan after compression

Look first at:

- Does `novel_context` consistently inject `chapter_plan`?
- Does `ctxpack/builder.go` receive `chapterPlan`?
- Does `writerRestorePack` refresh?

Key Files:

- `internal/tools/novel_context_builders.go`
- `internal/agents/ctxpack/builder.go`
- `internal/orchestrator/session.go`

#### Scenario 2: Compression loses character state/foreshadowing

Look first at:

- `LoadLatestSnapshots`
- `LoadActiveForeshadow`
- `ctxpack/builder.go`
- Has the Writer summary prompt been overridden?

#### Scenario 3: Compression is frequent but always misses store_summary

Look first at:

- Whether the current chapter is `<= 1`.
- Whether there are already recent summaries / arc / volume summaries.
- Whether `chapter_plan` or `current_outline` exists.
- Whether `writer.Context.Strategy` finally records `full_summary`.

#### Scenario 4: Insufficient context after recovery

Look first at:

- Whether handoff is generated.
- Whether restore pack refreshes.
- Whether recovery prompt injects handoff.

#### Scenario 5: Context swells due to too many tool results

Look first at:

- Did `ToolResultMicrocompact` apply?
- Inspect context rewrite events with `agent=writer|architect|editor` in slog: is `strategy` tool_result_microcompact or full_summary?

#### Scenario 6: One `novel_context` Result Exceeds the Window

Check first:

- The role's context-window source in startup logs. Unregistered custom-proxy models default to 200K; smaller models must declare their real window in `providers.<name>.models[].context_window` so compaction triggers correctly

## 11. Trade-offs in the Current Implementation

### Declared Directions

1. Do not stuff novel business logic into `agentcore`.
2. Prioritize relying on the structured store rather than chat history.
3. Writer uses a dedicated novel summary prompt.
4. Compression and recovery share the builder as much as possible to avoid discrepancies.

### Intentionally Retained Limitations

1. Only Writer uses `StoreSummaryCompact`
2. Store-based compaction does not apply in the first chapter
3. Insufficient store data falls back to `FullSummary`
4. `writerRestorePack` supplements, rather than replaces, `FullSummary`
5. Architect/Editor use microcompaction and `FullSummary`, without store-based compaction or restore packs

These limitations are not flaws, but boundaries set to control complexity at the current stage.

## 12. One-Sentence Summary

Context management in this project is not as simple as "shrinking long conversations," but rather:

`Prioritize using structured novel memory to maintain continuity, and let the LLM summarize conversations only when necessary; and rely as much as possible on the same set of persisted artifacts across compression, recovery, and handoff.`

If you modify this system in the future, prioritize keeping these three rules:

1. Do not make Writer's critical memory depend solely on chat history again.
2. Keep ctxpack strategy and restore data selection aligned.
3. For continuity problems, first verify that structured artifacts enter context, then decide whether prompts need changes.
